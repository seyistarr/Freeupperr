# Staging upload and registration review

Reviewed the staging upload-signature and asset-registration endpoints together with the protected asset validators. No deployment or database changes are included.

- **Environment gates:** both endpoints still require the exact preview branch, isolated staging marker, staging Supabase URL, staging Cloudinary cloud, and server configuration. Production and other branches remain rejected.
- **Signature ownership:** the signature endpoint validates the bearer token using Supabase `getUser`. It derives the staging folder from that verified user, generates the asset name server-side, and signs `type: authenticated` and `overwrite: false`. Request-body owner, folder, and delivery overrides have no effect. The response contains upload signing parameters and the public Cloudinary API key, without server secrets or delivery URLs. Signing authorizes an upload into the user's namespace; it does not authorize any post or register an asset.
- **Registration ownership:** the endpoint validates the bearer token, requires the owner's staging namespace, reads the target post from `privacy_test`, and checks that the verified user owns a restricted, visible, undeleted post. Unavailable posts are now rejected before the Cloudinary metadata lookup. Request post IDs require UUID structure.
- **Cloudinary delivery:** registration looks up the asset using server credentials and `type: authenticated`. The verifier now reuses `verifyStagingAsset`, so placeholder assets are rejected consistently along with public access mode, deleted assets, mismatched identity/type, invalid formats, and assets outside the 1-byte to 50-MiB limit. The registry stores only verified metadata, with owner, status and delivery type set server-side. The response contains only the registry ID and status.
- **Duplicate claims:** existing registrations are rejected even for the same post and owner. Lookup errors fail closed. Insert errors, including unique-constraint conflicts from concurrent requests, return a conflict without returning a registry ID. The registry must retain its `UNIQUE(cloudinary_asset_id)` constraint (specified in the existing review SQL); the pre-insert lookup alone cannot prevent concurrent duplicate claims. This review does not inspect or modify the live staging schema, so live constraint enforcement remains a staging verification requirement.
- **Browser caching:** every same-origin `/api/` request (and `/api` itself) bypasses CacheStorage reads and writes regardless of Authorization. Authenticated requests retain their existing bypass. Cache version v5 removes previous caches on activation; static assets retain cached/offline and network-cache behavior.

Validation: `npm run test:post-media` includes mocked endpoint execution for ownership, signed parameters, environment restrictions, asset validation, repeat registration and unique-conflict handling, plus service-worker cache/offline regression tests. No test calls a live database or uploads a Cloudinary asset.
