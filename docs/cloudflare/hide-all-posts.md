## Confirmed diagnosis and corrections

The browser client points to `https://api.freeupper.com`. Settings PATCH `profiles` with an owner ID filter. The Cloudflare gateway preserves the user's Authorization JWT, pins the project and anon apikey, rejects privileged credentials, and lets Supabase validate the token and select the database role. Its responses are private/no-store. The original failure is in Postgres: the legacy permissive administrator UPDATE policy SELECTs protected `profiles.is_admin` under the caller's role. `authenticated` has column-scoped SELECT, not table SELECT or SELECT on `is_admin`. Planning the UPDATE fails with 42501, even for an authorized owner. Other privacy flags using this UPDATE path are affected.

Production has ENABLE and FORCE RLS on profiles. `profiles_owner_update` has both `USING (auth.uid()=id)` and `WITH CHECK (auth.uid()=id)`. The migration retains those rules and repairs only the administrator policy's lookup. It grants no profile access and does not rewrite flags, posts, media, audiences, follow relationships or account records.

`public.is_admin_user(uid uuid)` exists, is owned by postgres, is STABLE SECURITY DEFINER, has an empty search path, and fully qualifies the profile table. EXECUTE is limited to postgres and authenticated. It returns a boolean, never a profile row. The new policy always supplies verified `auth.uid()`, so a caller-provided UUID cannot confer administrator rights. The deployed privileged-field trigger prevents a regular owner from setting `is_admin`. The shared helper is unchanged. Existing limitations: authenticated callers can query another UUID's boolean admin status; the helper checks the admin flag, not suspension. Changing that shared contract is outside this correction and needs a separate review.

The previous SQL omitted some count/relationship RPC paths and had no drift protection or rerun plan. Its small fixture also gave functions broader grants than production. The revised fixture uses captured production definitions, execution ACLs, actual approved follow edges, permanent/verification boundaries, and the privileged-profile trigger.

## Database changes

* A restrictive SELECT policy adds the hide flag as an additional AND condition on `posts`. Its owner bypass does not bypass any existing audience, publication, verification or permanent-retirement restriction. Public, Followers, Mutuals (`friends`) and Only Me values are unchanged.
* Five existing public short-link/SEO/sitemap RPCs deny hidden authors and require published, undeleted, unhidden public posts with a public, unsuspended author. They keep their original signatures, owners, SECURITY DEFINER status and exact ACLs. Anonymous-only SEO/sitemap grants stay anonymous-only.
* `authorize_protected_asset(uuid,uuid)` changes by exactly one predicate, apart from a review marker: `(p.user_id=p_viewer OR NOT coalesce(owner_profile.hide_all_posts,false))`. Every existing check remains: non-null verified viewer supplied by the trusted service; matching post and asset ownership; ready/authenticated asset; published, undeleted/unhidden post; unsuspended owner; asset/thumbnail membership in the post's media array; owner access; approved follower access; both approved edges for Mutuals. Only Me still matches only the owner. Its empty search path and postgres/service_role-only ACL are preserved. Browser roles cannot supply a forged viewer to this function.
* Search, bookmark listing, notification listing and sound statistics become SECURITY INVOKER. Their existing SELECT grants and RLS, including parent-post restrictions, decide visibility. Sound `total_uses` now counts visible published posts instead of returning the cached global `sounds.usage_count`; this intentional behavior change avoids hidden-post aggregate disclosure. Search retains its public-post/public-profile scope; owners still read and manage every allowed hidden post through their profile and direct authenticated UUID reads.
* Count-returning view/like/repost/bookmark/share/comment-like mutation RPCs keep their existing definer privilege needed for aggregate updates, but first call a new **private SECURITY INVOKER** guard. It accepts only a post UUID and derives identity from `auth.uid()`; it has no viewer parameter. It explicitly mirrors the current post read audience, approved-edge, hide, suspension, publication and authenticated retirement/verification rules. EXECUTE is postgres-only, so it runs only inside reviewed postgres-owned definer RPCs. It is not exposed as a public API. It must be reviewed with future audience-policy changes.
* The existing notification trigger suppresses newly created notifications to nonowners about hidden posts. No existing notification is changed. The deployed push function sends generic social notification text/IDs, not post bodies or media. Already delivered notifications cannot be recalled.

## Route audit

| Surface | Read path and enforcement |
|---|---|
| Home, video and studio feeds | `posts.js` loads `posts` with the caller JWT; restrictive post policies apply to each row and count. |
| Profiles, pinned posts, liked/saved/reposted posts | Direct or embedded `posts` reads use RLS; the owner bypass keeps hidden posts visible to their owner. Related reads inherit the production parent-post boundary. |
| Search, tags and recommendations | `search.js` uses direct `posts` reads. `search_posts` now runs as invoker. The legacy `find_similar_posts` RPC is absent from production; its client fails closed and also rehydrates IDs via post RLS. |
| Repost feed/view | Production `repost_feed_items` is already `security_invoker=true`. Its underlying `reposts` parent-post policy filters hidden originals. The feed also fetches original posts through RLS. No grants/view definition are broadened. |
| Comments, reactions, bookmarks, shares, views, hashtags, post media | Existing restrictive parent-post policies on these tables SELECT `posts` as the caller. New post hiding therefore propagates. Count-returning definer RPCs receive the additional session guard. |
| UUID direct links and previews in the app | `loadPostById` and `loadPostPreview` read `posts` using the caller JWT. Owners can access these links; unauthorized users get no row. |
| Public `/p/:code`, `/v/:code`, short-code lookup and reverse lookup | Anonymous RPCs explicitly check hide/audience/publication/author status. A hidden post's public crawler/short-link preview returns unavailable even for an owner visiting that anonymous surface; the owner can open it from their authenticated profile/UUID link. |
| Text/video OG images, SEO metadata, post sitemap | All public post RPCs are covered. Handlers and Cloudflare adapter use no-store; the adapter enforces private/no-store for dynamic output. Profile SEO describes profiles, not hidden post bodies. |
| Cloudflare API gateway/direct Supabase REST | Both reach the same RLS/functions. CORS is not the authorization boundary, and calling Supabase directly does not bypass hiding. Gateway tests preserve caller JWTs and mutation payloads without escalation. |
| Protected media and thumbnails | Production Edge Function `protected-media` v4 independently verifies `getUser(token)`, derives viewer ID from that identity, checks the service-only asset authorization RPC and the unchanged release gate, then proxies media. Cloudflare strips redirect/signing information and uses private/no-store for every response/range. The legacy Vercel path uses the same authorization RPC. |
| Trash, edits, delete/restore | `list_deleted_posts`, `edit_post`, `delete_post`, and `restore_post` are owner-scoped definer functions. They remain unchanged and owner management does not depend on the hide flag. Existing retirement and protected-media deletion behavior remains covered by the full regression suite. |
| Realtime | Production publishes posts, profiles, comments and reposts. New readable post rows are subject to subscriber SELECT RLS; this change does not revoke bytes already received, and DELETE events have platform-specific limitations. No publication changes are made. |

The live catalog had one public view and no public materialized views. All relevant existing read policies were inspected. Public relation grants, all 208 public/private RLS policies, triggers, column permissions and publication membership were checked. The route audit covers current repository handlers and the deployed protected-media/push functions; it is not a claim that unknown external consumers or independently stored copies can be revoked.

## Definer, grants and search-path review

The catalog contained 303 functions in public/privacy_v2_private, including 138 SECURITY DEFINER functions, all owned by postgres. [The inventory](hide-all-posts-definer-inventory.md) records owners' effective client/service execution exposure and search paths. Function bodies were screened for post/related-table reads, outputs, request identity and dynamic SQL. Post-body read functions, count-returning mutations, owner management, service-only publishing/cleanup, triggers, and related-table reads were reviewed in context. Dynamic SQL occurs in the private short-code allocator, DDL event trigger and settings updater; none exposes an arbitrary post-reading query.

No new definer function or client execution grant is introduced. CREATE OR REPLACE preserves all existing function ACLs and owners. Four read-only functions lose definer privilege. The new internal invoker helper is explicitly revoked from PUBLIC, anon, authenticated and service_role, and its resulting postgres-only ACL is asserted. Public/private schemas are not writable by client roles. Existing `public, pg_temp` search paths put pg_temp last; new SQL read functions and the new helper have an empty path and qualified relations.

The migration checks reviewed function bodies (line-ending-normalized hashes), owners, ACLs, security metadata, administrator-helper metadata and original audience/retirement SELECT policy predicates. Unknown production drift aborts the transaction instead of overwriting later work. Applying the reviewed transaction again is supported. Lock and statement timeouts limit deployment blocking. Future read-policy changes must also update the internal guard; its equivalence is covered by positive and negative audience tests.

Supabase's read-only security advisor still reports pre-existing mutable search paths and broadly executable definer functions outside this change. Relevant examples include `increment_comment_count` (void count mutation), obsolete bigint post APIs, trigger functions with default EXECUTE, and unrelated account/chat functions. These are follow-up hardening work, not certified safe by this review, and were not modified. Private tables with RLS/no policies intentionally deny browser access. Advisor references: [mutable search paths](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable), [anonymous definer execution](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable). OTD findings were not acted on.

## Verification and rollback

[hide-all-posts.VERIFY.sql](hide-all-posts.VERIFY.sql) contains read-only post-application catalog assertions for RLS, protected-column denial, owner policy, helper/service ACLs, ownership, reviewed bodies and function security modes. Run it only after a separately approved application. It is also exercised in the isolated database tests.

The authorization tests cover owner, approved follower, mutual, pending/unapproved follower, unrelated user and anon. They reproduce the original error; apply twice without changing any post row; check real execution grants, profile privilege-escalation denial, administrator behavior, feed/profile/direct-ID/related/RPC denial, sound aggregates, owner editing/deletion, media readiness/membership, private-account/suspension behavior, audience restoration and permanent-retirement denial. They exercise safe rollback/reapplication and rejection of unreviewed function drift. UI tests still verify persistence confirmation, zero-row failure and switch rollback. Existing API, browser, protected-publishing/media, retirement and Worker tests remain part of the full suite.

Rollback is [hide-all-posts.ROLLBACK.sql](hide-all-posts.ROLLBACK.sql). Before application, save a schema-only snapshot of the affected definitions/policies/ACLs and the approval commit. The migration is atomic: an application error rolls it back without post changes. Full rollback restores the reviewed original functions and admin policy, including the original permission defect, and removes the additional boundary/helper. **It refuses to run while any account has `hide_all_posts=true`**, because the original definer RPCs would expose hidden content. Do not clear user flags to bypass this check. With hidden accounts, keep restrictions and forward-fix, or disable affected endpoints while preparing a separately reviewed correction. No CASCADE, post deletion or data rewrite is used.

After approval/application, use real owner/follower/mutual/unrelated sessions and an anonymous browser to check persistence across reload, all feed/search/profile/direct-link surfaces, playback/ranges, owner edit/trash actions, unhide restoration and cross-owner update denial. Run catalog verification and a security advisor again. These live acceptance checks remain outstanding.

## Limits that remain

Previously downloaded/rendered content, search-engine/social caches, and public Cloudinary/Supabase URLs learned before hiding cannot be recalled by a database flag. This change prevents future application/database retrieval and new protected-media authorization, not access to independently known public asset URLs. Solving that requires a separate media-storage migration; no assets or existing posts were changed here. Long-running requests authorized before the setting commits can complete. Suspended-admin helper semantics, unrelated legacy count mutation RPCs and broader pre-existing advisor findings require independent review.
