# Private view-once: required backend contract (not implemented or enabled)

The current repository cannot honestly provide encrypted private view-once by adding an upload endpoint alone. There are no chat asset/key tables, encrypted upload/decrypt flow, key rotation/revocation rules, or audited claim-and-stream endpoint. The two intended Edge Functions are absent and blocked by the gateway. Existing public Cloudinary URLs and a UI timer do not meet these requirements.

A safe implementation can build on the existing authenticated gateway and Supabase authorization architecture, but requires a reviewed media/key lifecycle:

1. Decide key custody explicitly. Encryption at rest with server-held envelope keys is different from end-to-end encryption. If E2EE is required, define recipient device keys, authentication, wrapping, recovery, device revocation and group membership changes before coding. Do not replace E2EE requirements with server-side encryption.
2. Upload **ciphertext** to a private origin with authenticated, server-signed uploads. Store an opaque asset ID, owner, immutable conversation/recipient binding, format, nonce/authentication tag, encryption version, key reference, state and hard expiry. Never put plaintext media URLs or decryption keys in message metadata, activity events, logs or public thumbnails. Use an authenticated encryption construction and unique nonce; use a managed key service or a reviewed E2EE protocol, not an app-embedded secret.
3. Authenticate every request with verified Supabase identity. Verify current direct/group membership, blocking, sending permission, view-once support and reply target in the same conversation. Ownership/recipient/asset bindings must be immutable. Never trust a body `sender_id` or `viewer_id`.
4. Stage remote upload first; atomically publish the private asset reference, message, caption and `reply_to` after validation. A cleanup worker handles remote uploads left behind by cancellation/failure. Expose no media before commit.
5. Claim with a row lock/unique viewer claim and a database-authored deadline. Preserve the current 30-second opening limit and an independent hard asset/message expiry. Deny sender reopen, wrong recipient, blocked/removed users, repeated/replayed claims and expired messages. Define network-interruption semantics explicitly: fail closed rather than reissuing reusable credentials.
6. Return bytes or a reviewed encrypted delivery envelope through an authenticated, `private, no-store` endpoint; never a reusable signed download URL. Recheck membership/expiry before release. Include a validated absolute expiry in `x-freeupper-view-once-expires-at`; expose that header through CORS. Do not treat a UI timer as server expiry enforcement. If E2EE is chosen, implement and verify client decryption before enabling this response protocol.
7. Revoke object URLs, stop playback, clear retained references on close/expiry/page hide, and preserve the existing background shield. Already-received plaintext cannot be recalled, and screenshots/camera capture cannot be reliably prevented. Do not promise otherwise.
8. Provide `chat_private_view_once_capabilities()` only after the above is implemented and audited. Version 1 must return `enabled`, `protocol_version`, `encrypted_storage`, `atomic_claim`, `atomic_reply` and `server_expiry`; the current frontend requires all guarantees. This capability response is not an authorization substitute.
9. Add the exact Edge endpoint names to the gateway allowlist only after authentication/authorization/expiry tests, concurrent claim tests, encryption/ciphertext verification and direct-origin bypass tests pass. Production secrets and key configuration require separate approval.

Required tests include cross-user/cross-conversation asset substitution, role/membership revocation, blocking, two concurrent opens, replay, wrong key/nonce/tag, tampering, hard expiry during transfer, interrupted upload/publication, atomic reply preservation, orphan cleanup, cache denial, direct-origin access, memory/blob cleanup and physical mobile/PWA behavior.

Until that work is approved and complete, the frontend rejects new view-once sends. Historical legacy rendering is retained for compatibility, without claiming it offers encrypted private delivery.
